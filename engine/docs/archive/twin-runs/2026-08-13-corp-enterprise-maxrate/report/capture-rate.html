Where the packets go missing

Loss as a share of packets carried, which is the only fair comparison when the windows differ (26 s to 240 s). Three rungs are exactly zero. R4's bar is drawn at a 2 px minimum so it is visible at all — its real value is 10 packets in 31.7 million, and all ten were at the host's gretap, none at the sink. Every drop at R4b and R5 is the opposite: the sink's virtio receive ring, with the host side clean.

The gretap drops are not rate-correlated — 10 at 1.5 Gbit/s over 240 s versus 2 at 2.6 Gbit/s over 90 s. That argues against congestion and points at a per-frame property, most likely oversized/GSO frames from background twin traffic exceeding the tunnel MTU. Unconfirmed.

The qdisc was worth 60% of the ceiling

The gretap inherited fq_codel, the node's default queueing discipline — an AQM that deliberately drops to hold latency down. On a capture path, where the entire point is that every frame survives, that is a silent loss source. Same rung, same 90 s window, only the qdisc changed:

ip link set dev tapg_63256a txqueuelen 20000
tc qdisc replace dev tapg_63256a root pfifo limit 20000

Applied by hand, and it does not survive a tap re-apply: axRange creates the gretap and leaves the node default on it. Re-assert after every tap deploy, or fix it in the adapter. Honest caveat: this cleaned the 90 s window shown, but longer 120 s windows at R4b still found loss — which is precisely why the headline number is R4 and not R4b.

Multiqueue moved the wall off the sink

The sink's capture NIC was single-queue — net1 carried no queues=, so a 32-core appliance ran every mirrored frame through one virtio receive ring. Setting queues=8 hot-applied with no reboot and no loss of the static transport address:

Same rung, same ~2.6 Gbit/s, same deep-FIFO gretap qdisc — only the queue count changed. The sink went from the bottleneck to clean at every rate this twin can produce. What is left is a different constraint entirely: the tc mirred→gretap handoff, which starts logging overlimits past ~2.6 Gbit/s — all 17 tapped ports funnel into one single-queue tunnel netdev.

What actually limits it

1 · Sink NIC — fixed

Was the wall above ~2.4 Gbit/s: a 32-core box seeing Combined: 1, with every drop on tap104i1 (host→guest). Now queues=8, hot-applied, 8 rx + 8 tx queues host-side. The sink has not dropped a packet since, at any rate this twin can reach. Now the binding constraint is the single-queue gretap that all 17 tapped ports mirror into.

2 · Generation, below 2.4 Gbit/s

The persona driver's rendered client is a single-threaded loop, so one instance pegs exactly one core — measured at 94.1%. Offered load scales by adding sending hosts, never by raising volume: on one host. R1→R4 was generation-bound; the capture path was never the constraint until R4b.

Measured with a 6-stage drop-accounting harness: VM tap ifaces → tc mirror → gretap tx → sink vhost → sink NIC rx → gre-cap decap. Counters read from /proc/net/dev and tc filter statistics. Twin corp-enterprise-890c29b2, plan corp-enterprise-4fc62c80.
