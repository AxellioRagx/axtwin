integration · contracts & rollout

The seams, precisely

What crosses each boundary, in which direction, in what format — and the order we build it. Two repositories, one contract at each seam.

Coupling boundary — one-directional
aximprint may import axRange’s validator / planner / op-catalog to validate the config it emits; axRange imports nothing from aximprint. aximprint is an independent project on its own repo — the same rule that already governs scenario_ai_research.
1

Metadata in

axRange O2 sensors → aximprint ingest
CrossesSensor-generated metadata — Zeek logs (conn, dns, ssl, …) first; Suricata & packetXpress later.
FormatRaw sensor logs → normalized event model (Flow / Identity / Service / Alert / SensorHealth) via a per-sensor ingest plugin.
Noteaximprint is not a sensor; it runs on a sensor host and normalizes what the sensor emits.
2

Config out — the front door

aximprint synth → axRange te · tfc · tap
Crossestwin_config (structure) + tfc traffic profile (behavior) + tap plan (capture vantage).
FormataxRange tier YAML — deterministic, per-field provenance, passes axrange validate unchanged.
NoteThe missing front door: derives a config from real traffic instead of hand-authoring it.
3

Recapture

axRange deployed twin → O2 sensors → aximprint′
CrossesThe deployed twin’s own live traffic, captured through the same tap & sensor plane.
FormatIdentical to seam ① — a second aximprint instance ingests it with no new contract.
NoteReuses the standing O2 capture plane; nothing new on the wire.
4

Reconcile

aximprint drift report → operator / axRange
CrossesDrift & persona-coverage report; a tap-placement recommendation for axRange’s EW/NS visibility model.
FormatReport + an updated tap plan. Round-trip self-test gates promotion.
NoteOnly meaningful because synth is deterministic — a replay reproduces the same twin.
