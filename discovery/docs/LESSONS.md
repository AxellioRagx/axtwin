# LESSONS — feed-forward institutional memory (`LES-NNN`)

A living register of **durable, actionable lessons** the project has paid for once and should never re-learn: bug-classes, determinism traps, silent-default traps, ordering invariants, dead-ends, reversal hazards, reuse rules, and positive patterns. Each entry is a **rule future work honors**, not a diary — the `code-writer` and `code-reviewer` subagents consult it, a `PreToolUse` hook auto-injects the entries whose `Scope:` matches the file being edited (`scripts/inject_lessons.py`), and the `doc-writer` appends a new entry whenever a bug fix or a review finding surfaces something durable.

**Positioning** (distinct from its neighbors, CONVENTIONS §2):

- `docs/CHANGELOG.md` — what *was decided/built* (chronological, Authority-marked). Lessons link back via `Origin:`.
- `docs/OPEN_QUESTIONS.md` — *undecided* design topics (`Q<n>`), closed with a pointer to the resolution.
- **`docs/LESSONS.md` (this file)** — *actionable rules* to apply going forward, extracted from the above so a hook/agent can consume them.
- User/team working *preferences* live in the memory store (`~/.claude/projects/-home-rocky-aximprint/memory/`), not here.

**Never delete an entry.** If a lesson is superseded, keep it and add a forward-pointing note. IDs are stable — never renumber or reuse.

## LES-001 — Never version an incubating schema; ratification is the user's call

**Class:** reversal-hazard
**Scope:** "any incubating schema", `events`, `ingest`, `windowing`, `store`, docs
**Consumers:** code-writer, code-reviewer, doc-writer
**Rule:** The event model, feature shapes, plugin contract, and belief-store shapes carry **no version fields and no bump ceremony**, and change freely during incubation. Do not add version fields, bump ceremonies, compatibility shims, or "v1 schema" doc claims — not even as a courtesy. The axRange house rule "version-locked schema → confirm + bump" is **suspended here**, and the workflow framework was imported from axRange with that gate deliberately inverted: *changing* a schema is free, *ratifying* one is what needs the user. This is the single most likely habit to leak across from the sibling project. **Amended 2026-08-14 — one schema is now ratified, and this lesson is not weakened by it.** The **network IR** (`docs/WORK_ORDER_network_ir.md`, DESIGN_BRIEF §0.2's own amendment) is versioned by user ratification, which is exactly the mechanism this entry describes working correctly: the user ratified, Claude Code did not. Everything listed above stays incubating. **The discriminator, now that there is one of each to compare: a schema is versioned when something OUTSIDE its producer depends on its shape.** The belief store is read by one in-repo consumer that moves with it, so a mismatch is a build error (and `BeliefStore.__init__`'s schema guard makes it loud); the IR is read by a drift comparator, a diagram generator, a GNN harness and the twin compiler, on independent lifecycles, and will be re-read long after it was written. Cite that test rather than this entry's list, which is a snapshot of which artifacts currently sit on which side. Do **not** read one ratification as a phase change — the asymmetry is permanent by design, and treating it as a step toward versioning the rest is the same leak this entry has always been about, arriving from a new direction.
**Origin:** DESIGN_BRIEF §0.2 + §11, CONVENTIONS §1.2; CHANGELOG 2026-08-03 (workflow framework import)

## LES-002 — Re-verify determinism after touching the pipeline; never assume it

**Class:** determinism-trap
**Scope:** `windowing`, `learners`, `store`, `synth`, `src/aximprint/synth/synthesizer.py`
**Consumers:** code-writer, code-reviewer, tester
**Rule:** Two invariants carry the whole project — idempotent window close (same events + same build → identical features, DESIGN_BRIEF §5.4) and the deterministic compiler (same snapshot → byte-identical YAML, §9). They are what make backfill, reprocessing, and the round-trip self-test honest, and they break *silently*: a `set` iteration reaching an output, an unordered DuckDB result consumed as-is, an unseeded RNG, or a wall-clock call is enough. Run `python scripts/verify_determinism.py` after any change to these layers — the unit suite does not catch it, because a single run always agrees with itself.
**Origin:** CHANGELOG 2026-08-03 (workflow framework import — the invariants were stated in the design brief but unenforced by any check until then)

## LES-003 — Run data does not go in the repo, and aximprint's own appliance credentials are not run data

**Class:** repo-hygiene
**Scope:** "real capture data", `store`, `learners`, `acquire`, `acquire/client`, `acquire/auth`, `acquire/harvest`, docs
**Consumers:** code-writer, doc-writer, live-verifier, code-reviewer
**Rule:** **REWRITTEN 2026-08-12 (user ratification) — this lesson no longer constrains what aximprint COLLECTS.** It used to. The project's collection rule is now **forensic completeness**: every observed field is collected, nothing is refused on disclosure grounds, and `axrange` owns the disclosure decision (CONVENTIONS §3, DESIGN_BRIEF §7, CHANGELOG 2026-08-12). A parser that drops a password, a URI, a mail recipient or an LDAP DN "for privacy" is now **wrong** — it manufactures the exact ambiguity `evidence_class` exists to prevent, since a withheld field is indistinguishable downstream from one never observed. Do not cite this lesson to justify a field refusal, a redaction, or a skipped stem.

What survives, for reasons that were never about privacy and are stated here without it:

- **Run data does not belong in version control.** A belief store, evidence log, feature file, pcap or Zeek log directory derived from a real run is a *build output of a run* — it is large, it is not reviewable in a diff, it is not reproducible from the repo, and once committed it is permanent and pushed. Same reason a 9 GB pcap or a `.venv` does not get committed. **Report shapes, counts and distributions in docs, not contents** — "the harvester wrote 5 windows, 238.8 MB pcap → 2.1 MB metadata" is what a CHANGELOG entry is for; a dump of captured rows is not, because it is unreviewable noise in a document meant to be read. When a lesson comes from real data, write the *behavior* ("DHCP hostnames collide across VLANs in a large capture"), not the data — that is a writing-quality rule, and it is unchanged.
- **aximprint's own credentials are not observations.** `~/.config/aximprint/config.toml` and its password file, `AXIMPRINT_API_KEY`, `--ca-bundle` contents: these are *this tool's* authentication to the Xpress appliance, not facts it saw on the wire. Forensic completeness is about what the sensor observed; it does not license writing our own API key into a commit, a log line, or an exception message (`LES-039` is the same discipline for transport errors). Name the field, never the value.

**Superseded (2026-08-03, rewritten 2026-08-10, REVERSED 2026-08-12) — kept per this file's "never delete, supersede in place" discipline.** The old rule treated four categories as content that must never be written down. Categories 1 and 4 below are **no longer restrictions on collection**; the reasoning is preserved only so a reader of older CHANGELOG entries and work orders can tell what the project used to believe and why a `smtp`/`sip` decline or an `http` field refusal reads the way it does in those documents:
1. **Raw capture files** (`*.pcap`, `*.pcap.part`) — was "the most sensitive tier; never read, quote, or describe one beyond its shape." **REVERSED for collection** — a pcap is evidence and may be read and processed freely. What holds, for size not sensitivity: it is not a repo artifact, and a doc describes it by shape because a doc cannot usefully contain 9 GB.
2. **Credential material** — the config file's contents, the password file, any `*_API_KEY` value, `--ca-bundle` contents. **STILL HOLDS**, and now for the sharper reason that it was never an observation: this is aximprint's own authentication to the appliance, not a fact the sensor saw. Name the field, never its value (`LES-039` applies the same discipline to transport exceptions).
3. **Appliance identity** — hostnames, IP addresses, TLS certificate Common Names and SHA-256 fingerprints. **REVERSED for collection**: a cert CN observed in traffic is now an ordinary observed fact and `ssl`/`x509` parsers take it. Still **not** something to hand-type into a doc, for the reason in category 1 — a specific value in a CHANGELOG entry is unreviewable detail where the behavior was the point. Note the practical consequence: the two values redacted from `docs/RUNBOOK_CORPAPCN.md` and `docs/VENDOR_API_DEFECTS.md` on 2026-08-10 were removed, not archived, and `LES-071` confirmed they never entered git history — so they are **not recoverable** from this repo. Re-observe them if they are wanted.
4. **The original scope** — a belief store, evidence log, feature vector, or synthesized config derived from a real capture: PII, hostnames, user principals, cert subjects, filenames, cleartext credentials observed in traffic. **REVERSED, completely.** This is exactly what the store is *for* now. Collect all of it.

**Original rule (2026-08-03, scope rewritten 2026-08-10, collection scope REVERSED 2026-08-12 — kept for the record, per this file's own "never delete, supersede in place" discipline):** "A real capture — and every belief store, evidence log, feature vector, and synthesized config derived from one — may carry PII, hostnames, user principals, cert subjects, filenames, and cleartext credentials. Report shapes, counts, and distributions, never contents. Nothing capture-derived goes into docs, CHANGELOG, LESSONS, commit messages, or off the host."
**Origin:** DESIGN_BRIEF §7, CONVENTIONS §3; CHANGELOG 2026-08-03; rewritten CHANGELOG 2026-08-10 (`xtract`→`acquire` merge, step 9); **collection scope reversed by user ratification, CHANGELOG 2026-08-12** — forensic completeness replaced privacy as the governing principle, and this lesson was rewritten from a privacy rule into a repo-hygiene one.

## LES-004 — Never assume a sensor log is ts-sorted; bound the reorder in seconds, cap it in rows

**Class:** ordering-invariant
**Scope:** `ingest`, `ingest/zeek`, `src/aximprint/ingest/zeek/plugin.py`, "sensor log ordering"
**Consumers:** code-writer, code-reviewer, tester, live-verifier
**Rule:** Zeek keys a row on connection **start** and writes it at **close**, so a log is ordered by an event the row does not report — on the reference capture `conn.log` had 5.2 % of rows below the running max and `dns.log` 65 %. Never take "the sensor writes in order" from documentation or from a small fixture; **measure it, and measure it on both axes** — rows displaced and seconds displaced decouple as line rate changes, and a busy log can be badly out of order in rows while barely out of order in time. Size the reorder buffer on the **time** axis (a horizon in seconds, with headroom over the measured worst case) and keep a row cap as a *memory backstop only*: a row bound's real horizon is `capacity / row_rate`, so it silently weakens exactly as captures grow. When the row cap forces a flush, the horizon was **not** honored — count it and disclose it as a health fact, never as a debug line.
**Origin:** CHANGELOG 2026-08-03 (streaming Zeek ingest, closes `Q2`)

## LES-005 — Replacing an exact guarantee with a bounded one is a two-sided change; and any derived quantity that is a difference of two sensor-supplied numbers needs its own domain gate

**Class:** bug-class
**Scope:** `windowing`, `ingest`, `src/aximprint/windowing/windows.py`, `src/aximprint/windowing/entities.py`, "any accumulated value computed as a difference/delta of two values a sensor or upstream payload supplies directly"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** Swapping a global sort for a bounded reorder does not weaken a guarantee — it **replaces one contract with a different one**, and every consumer written against the old contract becomes a silent corruption site the same day. Harden the consumer *in the same change*: audit every min / max / delta / interval / index on the receiving side. Concretely, residual disorder produced negative interarrivals feeding a quantile sketch, a `last_ts` preceding its `first_ts`, and an inverted binding interval — none of which raised anything. Anything you refuse must be **counted**, not clamped silently. And note that indices go negative once ordering is only bounded: `int()` truncates *toward zero*, so a negative offset lands in bucket 0 and a `0 <= i < n` guard passes for the entire first bucket — use `math.floor` and reject the negative side explicitly. **Amended 2026-08-13 — the same failure recurred through a completely different mechanism, which is the part worth generalizing.** This lesson's origin incident was about the *ingest reorder buffer*: a bounded-not-exact ordering guarantee let a negative interarrival reach a sketch. `ingest/zeek/plugin.py::_ocsp` (`Q29`) produces `nextUpdate − thisUpdate`, a difference of two timestamps a sensor supplies **directly in one row** — no reorder buffer, no cross-event merge, both values individually well-formed and individually guarded against being unset (`_num`, never `_f`) — and a negative result could *still* reach a quantile sketch with every other health signal reporting clean, because nothing gated the **sign** of the subtraction itself. **State the general form, not the mechanism that first taught it**: any derived quantity computed as a difference of two sensor-supplied numbers needs a domain gate (here, `>= 0`) with a **counted refusal** before it reaches an accumulator, regardless of *why* the two numbers might disagree — reorder-induced disorder, a responder's own clock skew, or some future third cause. Checking "is each input individually valid" is not the same check as "is the *derived* value plausible," and a design that only does the former will keep rediscovering this one input at a time. This recurrence is itself an instance of `LES-090` (a lesson recorded from one mechanism is read as being about that mechanism, not the invariant it demonstrates) — read this amendment, not the original incident alone, before writing the next difference-of-two-sensor-numbers accumulator.
**Origin:** CHANGELOG 2026-08-03 (window layer hardened for bounded disorder); amended CHANGELOG 2026-08-13 (`docs/WORK_ORDER_subject_less_facts.md`, code review `M2`), `src/aximprint/windowing/windows.py::WindowManager._add_profile`; `LES-090`.

## LES-006 — A health field separates "no evidence" from "evidence of none" — and is attributed to the window the evidence describes

**Class:** silent-default-trap
**Scope:** `windowing`, `src/aximprint/windowing/windows.py`, `events`, "window health record", `_SERVICE_NOT_PROJECTED`, "a decline reason citing an unmeasured property"
**Consumers:** code-writer, code-reviewer, live-verifier, doc-writer
**Rule:** `capture_loss_pct_max = 0.0` because nothing was audited is a **false clean bill of health**; the honest answer is `None`, and any checker that reads `None` as a failure is checking the wrong thing. Two further rules follow. (1) **Attribute evidence to the window it describes**, not the window that happened to be open when it arrived — a late `SensorHealthEvent` moved loss evidence to the neighbouring window, quietly making one window look clean and another look worse. (2) **An audit that only reaches stderr is not an audit.** Provenance must land in a persisted artifact — the ingest disorder count is a `SensorHealthEvent` precisely so the window health record can inherit it. §5.4 #5's claim is that the asterisk *travels*; a number printed to a terminal travels nowhere. (3) **Amended 2026-08-13 — the same distinction applies to a DECLINE REASON, not only a data field.** "Plausibly high-cardinality" and "measured at 3 distinct facts from 278 rows" read as the same kind of prose claim, and they are opposites: a guess and evidence of none. `_SERVICE_NOT_PROJECTED["smb_files"]` (`docs/WORK_ORDER_zeek_stem_coverage.md` build step 2b) named a cardinality concern for a count nobody had actually taken once `name` joined the collected fields — a legitimate worry, indistinguishable in the prose from a finding. A decline reason resting on an unmeasured property must **say** it is unmeasured and name the measurement that would settle it, or a reader cannot tell "nobody checked" from "checked, and it's bad" — this entry's failure, one layer up in narrative rather than in data.
**Origin:** CHANGELOG 2026-08-03 (window layer hardened for bounded disorder); (3) CHANGELOG 2026-08-13 (build steps 2/2b land, code-review round), `docs/WORK_ORDER_zeek_stem_coverage.md` build step 2b.

## LES-007 — Parse the boundary strictly: unset is not zero, and a short row is not a row

**Class:** silent-default-trap
**Scope:** `ingest`, `ingest/zeek`, `src/aximprint/ingest/zeek/plugin.py`, "sensor parse boundary"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** At a sensor boundary, **unset is a distinct value from zero**: `_f(v, 0.0)` on an absent counter manufactures an *observed* zero and pollutes every statistic downstream. Carry the distinction (`None`, plus a flag such as `counters_imputed` so consumers can see it) rather than defaulting. Take the unset/empty markers from the **format's own header** (`#unset_field` / `#empty_field`) — a hardcoded constant is a guess about someone else's writer. Check arity too: `dict(zip(fields, row))` succeeds on a truncated row and yields a *complete-looking* event, which is strictly worse than a parse error. A column-count mismatch is a rejection, per "fail loud, fail closed" (CONVENTIONS §3).
**Origin:** CHANGELOG 2026-08-03 (window layer hardened for bounded disorder)

## LES-008 — A cheap proxy is not a check: parse the value, don't pattern-match its shape

**Class:** bug-class
**Scope:** `ingest`, `ingest/zeek`, `learners`, `src/aximprint/ingest/zeek/plugin.py`, "evidence_class observed"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** Deciding a DNS answer was an IPv4 address by `a.count(".") == 3` bound **1,355 of 3,936 dns-derived identity events (34.4 %) at `evidence_class="observed"` to strings that were never addresses** — fabricated provenance, which is worse than a missing binding because it propagates into the synthesized config unchallenged. Never infer a type from its shape; **parse it** with the real parser and let the parse failure be the classifier. The same rule covers truthiness: `if not ts` accepts `NaN` and `inf`, and `if last_flow_ts` conflates epoch 0 with "unset". Test for the property you actually mean — `is None`, `math.isfinite`, a successful parse — never for a proxy that is merely correlated with it.
**Origin:** CHANGELOG 2026-08-03 (window layer hardened for bounded disorder)

## LES-009 — No output byte may depend on arrival order or the clock

**Class:** determinism-trap
**Scope:** `ingest`, `windowing`, `features`, `store`, `src/aximprint/features/jsonl.py`, `src/aximprint/ingest/zeek/plugin.py`
**Consumers:** code-writer, code-reviewer, tester
**Rule:** Three concrete disciplines behind `LES-002`. (1) **A k-way merge needs a total order that terminates before the payload.** `heapq.merge` breaks ties on *argument position*, so sort the input paths, key each intra-file heap on `(ts, row_index)`, and make sure the comparison can never reach the payload — if the payload happens to be orderable the bug stays invisible until the data changes, which is the worst possible failure schedule. (2) **Sort rows by key at the persistence boundary**, so a file's bytes depend on row content rather than an upstream dict's insertion order. (3) **Confine wall-clock to exactly one named, exported field**, so a determinism check can assert the *set* of differing keys instead of maintaining a skip list that rots as fields are added.
**Origin:** CHANGELOG 2026-08-03 (streaming Zeek ingest; feature-vector sink)

## LES-010 — Know both cost axes at window close: peak accumulator memory and per-window output volume

**Class:** perf-cost
**Scope:** `windowing`, `features`, `src/aximprint/windowing/sketches.py`, `src/aximprint/windowing/windows.py`
**Consumers:** code-writer, code-reviewer, live-verifier
**Rule:** **Top-K eviction at close bounds output size, not peak memory** — everything the window accumulated still existed a microsecond before the eviction ran. And the accumulator that hurts is not the obvious one: `self._edges` is bounded by peer cardinality, while the exact `Quantiles` stand-ins retain *every value* (3 per flow per window), making them O(input) where the design says O(output). DESIGN_BRIEF §5.2's "bounded at any line rate" describes the probabilistic target, **not** the v0 stand-ins — do not quote it as if the stand-ins honored it (`Q8`). On the output axis, an artifact that re-emits unchanged state instead of a delta pays for it every window: `identity.jsonl` is 98.4 % restatement and 17 % of the archive because the resolver returns a record on every *observation*, not on every *change* (`Q9`). Check an artifact's emit condition against the noun in its name.
**Origin:** CHANGELOG 2026-08-03 (feature-vector sink; streaming Zeek ingest findings)

## LES-011 — A feature archive inherits the capture's sensitivity; a sink defends its own output directory

**Class:** privacy
**Scope:** `features`, `src/aximprint/features/jsonl.py`, "real capture data"
**Consumers:** code-writer, code-reviewer, live-verifier
**Rule:** Feature vectors, manifests, and every other artifact derived from a real capture are capture-derived and carry the capture's sensitivity in full (`LES-003`) — statistical compression is not anonymization. A repo-level ignore rule keyed on one extension is not protection: the repo's `*.jsonl` line would have missed `manifest.json` entirely. The output sink therefore writes a `.gitignore` containing `*` into **its own destination directory** at open time, so a mis-targeted `--out` inside the repo cannot become a commit. A component that can write capture-derived data is responsible for making that data uncommittable where it lands.
**Origin:** CHANGELOG 2026-08-03 (feature-vector sink)

## LES-012 — Sensor health columns can be present-but-empty; `capture_loss` may be the only loss signal

**Class:** env-fact
**Scope:** "real capture data", `ingest/zeek`, `ingest`, `live-verifier`
**Consumers:** live-verifier, code-writer, tester
**Rule:** On the reference deployment, `stats.log` carries the `pkts_dropped` and `pkt_lag` **columns** with every one of 1706/1706 cells unset — a schema present, a signal absent — so `capture_loss.log` is the only loss evidence available and `sensor_pkts_dropped` / `pkt_lag` are legitimately `None` in all 72 windows. Do not read that `None` as a parse bug or a coverage gap. Second fact from the same capture: **loss is non-zero in 100 % of windows** (5.87 %–24.92 %, median 9.17 %) — there is no clean window, so any code path or verification step that implicitly expects one is testing an assumption this environment does not satisfy (`Q10`).
**Origin:** CHANGELOG 2026-08-03 (streaming Zeek ingest — real-capture findings)

## LES-013 — Sorting *derives* an order; it never repairs one you were given, and it never fixes a float

**Class:** ordering-invariant
**Scope:** `features`, `src/aximprint/features/vocabulary.py`, `src/aximprint/features/jsonl.py`, `windowing`, "any pinned vocabulary"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** `LES-009`'s "sort at the persistence boundary" means *derive* a deterministic order from an **unordered** structure — a dict, a set, an accumulator. It does **not** license re-sorting an order someone handed you. A **pinned index map is read in the order given, never re-sorted**: position in the list *is* the tensor column, so re-sorting at load silently renumbers every column after the insertion point, and a map may therefore be append-extended without renumbering. The round-trip is the test — re-pinning to an archive's own manifest must reproduce its map exactly. The mirror-image error is just as expensive: a `sorted()` was added to a loop citing `LES-009`, but every mutation in that loop was per-key, so cross-key order could not affect any value; the real order-dependence was one line below in **float accumulation** — measured drift `…607.18976` vs `…607.18758` at 200k rows, surviving `round(x, 6)`. Sorting does not make `+=` associative. Before you sort for determinism, name the specific quantity that would otherwise vary, and if that quantity is a float sum, reach for compensated (Neumaier) summation instead.
**Origin:** CHANGELOG 2026-08-04 (pinned categorical vocabulary, closes `Q6`)
**See also:** `LES-032` — a *k-way merge* is not a sort, and that distinction runs the other way: it
*licenses* a merge key richer than the order actually checked at the input boundary, which this
entry's own "never re-sort an order you were given" could otherwise be misread as forbidding.

## LES-014 — A bound stated in a comment is not a bound: cap data-keyed state at insert, and disclose the cap in the artifact

**Class:** silent-default-trap
**Scope:** `features`, `sinks`, `src/aximprint/sinks/base.py`, `src/aximprint/features/vocabulary.py`, `windowing`, `src/aximprint/windowing/sketches.py`, "any map keyed on data"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** Any map whose **keys are data** grows with an adversary's imagination, not with your design. 36,000 rows minting fresh dynamic-port labels produced 144,000 keys and **17.6 MiB retained — pinned or unpinned**, because the per-key OOV counters are kept regardless; one wide row made the manifest **3.8× the row file it described**, defeating the read-the-manifest-then-stream premise it exists for. Four rules. (1) **Cap at insert, not at close** — eviction at close bounds output size, never peak memory (`LES-010`). (2) **The cap belongs in the artifact**, with spill counters, and **truncated mass must not count toward any completeness statistic**: the uncapped run reported a 16,385-column index at `coverage: 1.0`, and *a bounded map that reports itself complete is worse than an unbounded one* — post-cap the same data honestly reports `0.003556`. (3) **State the bound where the state is declared**, not in prose elsewhere: the sink contract still claimed sinks "hold nothing across windows" in the very file this change gave run-level state. The honest contract is *a sink retains no **window**, but may hold run-level state provided the bound is enforced at insert and every truncation is disclosed.* (4) **Test the property, not the shape** — the streaming test scanned `vars()` for `list` / `tuple` and so could not see state held inside an object at all. Assert the bound.
**Origin:** CHANGELOG 2026-08-04 (pinned categorical vocabulary, closes `Q6`)

## LES-015 — Every field in a self-describing artifact must answer the question its name implies — check that it can

**Class:** bug-class
**Scope:** `features`, `src/aximprint/features/vocabulary.py`, `src/aximprint/features/jsonl.py`, `store`, "any self-describing artifact"
**Consumers:** code-writer, code-reviewer, tester, doc-writer
**Rule:** A manifest is only as good as its weakest field, and a field that *looks* authoritative is worse than a missing one. Two failures from one round. (1) **Digest the value, not the container.** `pinned_to.sha256` hashed the pin *file*, which carries a wallclock block — so two archives pinned to an identical map reported different digests, and the single field meant to answer "did these encode to the same columns?" structurally could not. Split it: `file_sha256` for provenance, `map_sha256` for the question. (2) **`container` is a shape, not a unit.** Two fields declared identically as `container: "dict"` carried a byte *proportion* (~1.0 per row) and a raw *count* (over 1.5 M) — three orders of magnitude apart, with nothing to tell a manifest-only consumer whether to normalize. A number crossing an artifact boundary carries its units beside it (`weight: proportion | count | indicator`). The general check: for each field, write down the question a consumer will ask it, then confirm the value can actually answer that question and nothing weaker.
**Origin:** CHANGELOG 2026-08-04 (pinned categorical vocabulary, closes `Q6`)

## LES-016 — Before pinning a vocabulary, ask what kind of non-atom a key is: a joined *set* or a joined *tuple*

**Class:** pattern
**Scope:** `features`, `src/aximprint/features/vocabulary.py`, `windowing`, `src/aximprint/windowing/windows.py`, `ingest/zeek`
**Consumers:** code-writer, code-reviewer, doc-writer
**Rule:** Sensor vocabularies arrive pre-joined into strings, and the join character hides **two different problems that must not be treated alike**. A joined **set** (Zeek `service`, separator `,`): variable arity, combinatorial in the power set, and composite keys coexist with their own singletons as unrelated dimensions — splitting it changes what a *value* means (duplicate the proportion across atoms, or divide it and assert a split nobody measured), so it is a feature-semantics decision and must be **deferred with its impact measured and published**, not performed. A joined **tuple** (`"<port>/<proto>"`, separator `/`): fixed arity, bounded by a product rather than a power set, value-neutral to decompose, and its unbounded tail comes from exactly **one** dimension — which can be binned. Note also that a tuple's pairing may itself carry information (the same port under two transports), so it does not decompose into independent marginal one-hots either. Check whether the tuple already exists upstream as a real tuple: `listen_ports` is a genuine `Counter[(port, proto)]` string-joined purely to be JSON-representable, and the right fix lives where the key is minted, not where it is published.
**Origin:** CHANGELOG 2026-08-04 (pinned categorical vocabulary, closes `Q6`); `Q12`

## LES-019 — A columnar store speeds up what you *skip*, not what you read row-at-a-time

**Class:** perf-trap
**Scope:** `ingest`, `ingest/zeek`, `src/aximprint/ingest/zeek/sources.py`, `store`, `parquet`, `duckdb`, "columnar", "performance"

## LES-022 — Reject a repeated destination before opening any of them — a datastore's willingness to open a second connection is not a safety net, and a destination's mere existence is not evidence it was ever written to

**Class:** bug-class
**Scope:** `sinks`, `store`, `src/aximprint/cli.py`, `src/aximprint/store/belief_store.py`, "duckdb", "any fan-out to N destinations"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** `--store b.duckdb --sink store=b.duckdb` used to exit 0 and write every window **twice** into `b.duckdb` (measured: 584/1452/1828/192/8 rows against a true 292/726/914/96/4 across the five row-bearing tables, two `runs` rows each independently claiming the full window count) — because **DuckDB does not refuse a second connection to a path already open in the same process with the same configuration; it opens one, and both connections write.** DuckDB only refuses a second connection on a **configuration mismatch** (e.g. a `read_only=True` connection racing a read/write one to the same file) — never merely because the path is already open. An earlier assumption in this round's own design went the other way — that the second connection would simply be refused, so no explicit guard was needed — which is exactly backwards; the mechanism was confirmed by hand (see `tests/test_sinks.py`'s notes on `test_open_sinks_rejects_two_specs_resolving_to_the_same_destination` and `test_store_sink_run_row_only_appears_on_a_clean_close`) before the guard was written. **Verify a datastore's actual concurrency policy empirically; do not assume the safer-sounding direction.** Two more facts a verification step must know before trusting a "nothing was written" check: DuckDB **creates the file at `connect()` time**, before a single row is inserted, so a destination's mere existence on disk proves nothing about whether it was written to — assert on content (a table's row count) instead; and `abort()` (`LES-023`) does not retroactively delete anything a sink already wrote before a later sink's failure, so the only real fix is to reject **before opening anything at all**. `cli._reject_repeated_destination` resolves every `--sink`/alias destination to an absolute path (so a relative and an absolute spelling of the same file collide too) and compares every sink *type* against every other, before the first sink's `open()` runs. The rule survives the DuckDB specifics: when a fan-out can address N destinations, validate the whole address set for collisions up front — never rely on the underlying resource to reject a double-write for you, and never use a resource's mere existence as proof nothing landed in it.
**Origin:** CHANGELOG 2026-08-06 (egress: one sink registry, both output paths through it), `docs/WORK_ORDER_egress_sink_unification.md` (`M1`)

## LES-023 — A fan-out has three failure surfaces (open / write / close); releasing what is open is not the same as completing it, and every surface needs the release half

**Class:** bug-class
**Scope:** `sinks`, `src/aximprint/sinks/base.py`, `src/aximprint/cli.py`, "any multi-destination fan-out with a completion artifact"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** Writing N destinations from one closed window is one logical operation with **three** places it can fail — opening sink K (sinks `0..K-1` are already holding a connection/handle), writing a window to sink K (every opened sink, ahead of and behind K, is mid-run), and closing sink K (sinks after it in close order have not closed yet). Before this round only the write surface was handled at all, and even there a failure just left each sink's own artifact in whatever state it happened to be — no released resources, no distinguishable "this run did not finish" signal. The fix adds `abort()` to the sink contract, alongside `open`/`write_window`/`close`, called on **all three** surfaces instead of `close()`: **`abort()` releases what a sink holds open WITHOUT writing that sink's completion artifact** (`manifest.json` for `jsonl`, a `runs` row for the store) — because that artifact's entire meaning is "this run finished," and writing it from a failure path fabricates the claim for a run that did not. The distinction is not academic: `jsonl` signals "unfinished" purely by `manifest.json`'s **absence**, so calling `close()` on a failure surface — even a `close()` that "only" writes the summary — would produce a directory indistinguishable from a successful run. Three consequences worth generalizing past this codebase. (1) A failure during `open()` releases every sink that already opened (`0..K-1`), not just the one that failed. (2) A failure during `write_window` releases **every** opened sink, including ones that themselves wrote every window successfully so far — a sink's own track record does not exempt it from a run-wide failure. (3) A failure during `close()` releases every sink not yet closed, while sinks that already closed cleanly stay untouched — their completion is individually real even though the run as a whole did not finish, and nothing can or should retract it. The reusable shape: a resource lifecycle with a completion ceremony needs a **release-only** exit distinct from the completion exit, reachable from every failure surface — "we call `close()` less often now" is not the same fix as "we have a way to release without completing."
**Origin:** CHANGELOG 2026-08-06 (egress: one sink registry, both output paths through it), `docs/WORK_ORDER_egress_sink_unification.md` (`M4`, `M5`)

**Class:** determinism-trap

**Consumers:** code-writer, code-reviewer, tester

## LES-029 — Consolidating N streams into one moves the buffers; it does not remove them

**Class:** perf-cost
**Scope:** `ingest`, `ingest/zeek`, `src/aximprint/ingest/zeek/sources.py`, "any k-way merge consolidating several sub-streams behind one exposed stream", "reorder buffer"
**Consumers:** code-writer, code-reviewer, tester, live-verifier
**Rule:** Reducing the STREAM COUNT a caller sees is not, by itself, a memory bound on what is inside the one stream it now sees. `LogDirSource`'s window-tree mode consolidated N window-directory files per log stem into one `ZeekStream`, mirroring how `ParquetArchiveSource` already uses one stream per log type rather than one per partition file — but a module docstring claimed that consolidation *bounded memory* the way it bounds the stream count `plugin.py` holds open, and that claim was false. `heapq.merge`'s own initialization primes every argument (pulls each one's first item) regardless of how many there are, so every sub-stream's own reorder buffer still exists — one per window directory — and each one fills completely before the merge can even begin comparing heads, whenever a leaf's own key span sits inside the reorder horizon (the *normal* case for one pcap window against a 600 s horizon, not an edge case). Measured: 670 MB resident at 300 window directories × 2,000 rows (417 MB for the identical corpus read flat) — and 669 MB of that was resident before the merge produced its **first** event. The general shape, stated once so it does not have to be re-discovered per layer: **a k-way merge's peak memory is O(open leaves × per-leaf buffer size), independent of which layer owns the leaves** — moving N buffers from a caller's view into a callee's internals changes who can *see* them, not how many exist or how large each one grows. `LES-010` already names accumulator memory as an axis distinct from output volume; this is the same axis showing up one layer lower, in a different kind of accumulator (a reorder buffer, not a sketch). The fix (`M1`, a user ruling) gives the STEM an aggregate row budget (`max(reorder_rows // len(paths), 64)`) rather than the full budget per leaf — trading repair quality (made visible via `source_capped`, `LES-028`, rather than paid for silently in RAM) for the bound. **Cost scales with per-leaf size, benefit (repair) scales with disorder** — a corpus sized to show the consolidation pass is *cheap* is not evidence it is cheap on the corpus that shows it is *useful*: a small, low-disorder synthetic fixture will not reproduce this cost, and neither the cost nor the benefit can be reasoned from the other. Measure both, on a corpus shaped like the real one — many leaves, each spanning less than the horizon.
**Origin:** CHANGELOG 2026-08-10 (multi-window Zeek log-directory read, closes `Q18`), `docs/WORK_ORDER_multi_window_log_read.md` (`M1`), `LES-010`

## LES-030 — Auto-detecting an input layout is a positive gate on a declared shape, or it is a sniff — and `float()` is a weaker check than it looks

**Class:** bug-class
**Scope:** `ingest`, `ingest/zeek`, `src/aximprint/ingest/zeek/sources.py`, "any auto-detected input layout/transport mode", "any format-sniffing gate"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** A mode switch between two input shapes needs a check that the evidence actually supports the shape being NAMED, on every branch that could take it — a structural sniff ("no direct log file under root, but there is at least one subdirectory, so this must be a window tree") is not a check, it is a guess wearing one's clothes. Measured false positives from the original structural-only gate: a single stray root-level `.log` file silently flipped 1 stream into 51; an `archive`/`backup`/`scratch` sibling directory was announced as a genuine 3-window tree; Zeek's own native `<date>/<time-range>.log.gz` rotation layout was silently reinterpreted as a window tree (the OUTPUT stayed correct, but unannounced, for the single most common real deployment shape); a `.git`-shaped subdirectory swept in and reported UNRECOGNIZED. Fixed with a genuine positive gate (`_looks_like_window_id`) *plus* a note on every branch — not only the one that fires — naming the shape chosen and why: "observable in exactly the direction that does not matter" (an operator can see a chosen mode's OUTPUT, never the reasoning that chose it) is a real gap, not a cosmetic one. A second pass then found the positive gate ITSELF was checking a proxy, not the shape — `LES-008`'s exact mistake recurring one layer up: gating on "parses as a finite float" (`float(name)`) rather than on the actual digit shape the real producer (`timeutil.format_instant`) emits. **`float()` is far more permissive than its one-line summary suggests, and every extra thing it accepts is a plausible real directory name**: a leading sign (`-1`, `+100`), scientific notation (`1e5`), PEP-515 underscore digit grouping (`1_000`, and — the realistic collision — a human-dated backup folder `2026_08_10` sitting right next to a genuine harvest tree), surrounding whitespace, and Unicode decimal-VALUE digits that are not ASCII at all (`٣٤`, Arabic-Indic). Tightened to `re.compile(r"[0-9]+(\.[0-9]+)?").fullmatch(name)` — `[0-9]` instead of `\d`, because the explicit range is not Unicode-aware where `\d` is; `fullmatch` instead of a hand-anchored `^...$` used with `match`, because `$` carries a documented exception matching just before a trailing newline that `fullmatch` does not share — **plus** `math.isfinite(float(name))` kept as a *second*, still-necessary gate: a long enough all-digit run (~400 nines, no decimal point) still passes the shape regex and overflows `float()` to `inf`. Both stages were verified for **no false rejects**: every shape the real producer can actually emit still passes. Note the distinction from `LES-013`, made explicit because it is easy to blur: validating a directory NAME's shape, to decide whether a mode applies at all, is not the mistake `LES-013` warns against; ORDERING rows by that name would be — this gate only ever decides which mode reads the tree, never in what order its rows are emitted, which still comes from each row's own parsed `ts`.
**Origin:** CHANGELOG 2026-08-10 (multi-window Zeek log-directory read, closes `Q18`), `docs/WORK_ORDER_multi_window_log_read.md` (`M3` and the second fix round's window-id-gate hardening), `LES-008`, `LES-013`

## LES-031 — A regression test's discriminating power is a property of the code it guards, not of the test; re-verify by mutation after the code changes, not only after the test changes

**Class:** tool-gotcha
**Scope:** `tests/test_zeek_ingest.py`, "any regression test written to catch one specific bug", "mutation testing", `ingest`, `ingest/zeek`
**Consumers:** tester, code-writer, code-reviewer
**Rule:** A regression test's ability to catch the bug it was written for is not fixed at the moment it is written — it is a property of the CODE it guards, and fixing that code can silently disarm the test with nothing to signal it happened. Demonstrated by reintroducing the original cross-window double-report bug into `sources.py` and re-running the suite: code-writer's own exactly-once test failed (as intended), tester's newer write-at-close test failed (as intended) — but tester's ORIGINAL shuffle-based fuzz test, written before `M1`'s per-substream aggregate-budget fix existed, **passed**, i.e. it did not notice the reintroduced bug. The mechanism: once `M1` floors each sub-stream's reorder budget (`LES-029`), a uniform shuffle of a small per-window file essentially never drives the inner reorder pass's own inversion-detection branch any more — the fix that made memory bounded also, as an unplanned side effect, made the fuzz test's own input shape stop exercising the code path it existed to guard. Nothing about the test's own text changed, and nothing failed to warn anyone — the suite stayed green throughout, because the test still proves a true and useful fact (no data loss under a random shuffle), just not the ONE fact it was originally written to prove. Fixed by keeping the original test (still valid, for what it actually shows) and adding a companion built on the REAL write-at-close shape the bug actually depends on, then confirming *its* discriminating power the same way — by reintroducing the bug and watching it fail. **The general rule: verify a regression test's power by actually reintroducing the bug it targets and re-running, not by reading its assertions and reasoning that they still look like they cover the case — and re-run that check whenever the code underneath the test changes, not only when the test's own text changes.**
**Origin:** CHANGELOG 2026-08-10 (multi-window Zeek log-directory read, closes `Q18`), `docs/WORK_ORDER_multi_window_log_read.md` (consolidated fix round, mutation-testing finding), `LES-029`

## LES-032 — Addendum to `LES-013`: a k-way merge is not a sort, and that licenses a merge key richer than the order actually checked at the boundary

**Class:** ordering-invariant
**Scope:** `ingest`, `ingest/zeek`, `src/aximprint/ingest/zeek/sources.py`, `docs/SPEC_zeek_metadata_archive.md`, "any heapq.merge / k-way merge across several independently-sorted inputs", "any merge key richer than the writer's declared sort"
**Consumers:** code-writer, code-reviewer, doc-writer, tester
**Rule:** `heapq.merge(*iterables, key=...)` preserves each INPUT's own items in that input's absolute order; the key only ever decides which input's *current* head compares smallest, i.e. how DIFFERENT inputs interleave with one another when their keys collide or run concurrently. So a partition or file that is contractually sorted on `ts` **alone** (the actual, checked contract — `docs/SPEC_zeek_metadata_archive.md`'s `sorted_by: "ts"`) can safely be merged with a richer key, `(ts, _zeek_run, _row_no)`, **without** requiring the writer to have produced that richer order: the extra fields only ever break a tie on `ts` **across** files, matching the archive's own declared total order for provenance, and can never reorder any one file's own rows — `_archive_row_key`'s docstring was rewritten in this round to say exactly that, rather than the stronger, unearned claim ("the contract requires `(ts, _zeek_run, _row_no)` order") an earlier version made. This is the complement to `LES-013`, not a contradiction of it: `LES-013` forbids re-deriving an order you were *given* (sorting when you should trust or repair); this entry is about a *merge* key, which is never re-deriving anything — it is the tie-break used to interleave several ALREADY-independently-sorted inputs, and it may legitimately depend on more information than the one field the writer's contract commits to. This round's fix to `docs/SPEC_zeek_metadata_archive.md` reflects the same correction at the spec-prose level: it no longer claims the reader issues `ORDER BY ts, _zeek_run, _row_no` (a literal, and false, SQL claim since `LES-019`'s "do not re-sort what the writer already sorted"), and states instead what the merge actually requires of partition sort order — `ts` alone, checked at open. The practical corollary: **type-check the ONE field the key structurally depends on for orderability** (here, `ts`) **at the boundary** — a wrongly-typed `ts` does not raise, it makes every row compare as `-inf` and silently degenerates the merge back into the exact path-order concatenation it exists to replace (`S2`, `load_manifest`'s `_ARCHIVE_KEY_COLUMN_TYPES`).
**Origin:** CHANGELOG 2026-08-10 (multi-window Zeek log-directory read, closes `Q18`), `docs/WORK_ORDER_multi_window_log_read.md` (`S5`), `LES-013`, `LES-019`

## LES-036 — `stream_ids` is passed through verbatim; never re-emit it in a different grammar

**Class:** bug-class
**Scope:** `acquire/catalog.py`, `acquire/windows.py`
**Consumers:** code-writer, code-reviewer
**Rule:** `stream_ids` is a spec string with its own grammar — `n[,n][,n-m][,n..m]`, `n`/`m`
integers in `0`–`4294967296`, with **both `-` and `..`** legal as range separators (documented only

for local cataloguing (gap detection, cross-checking against `fs/files`), but that expansion is

**Scope:** `acquire/runner.py`, `acquire/manifest.py`

**Origin:** CHANGELOG 2026-08-05 "Q1–Q4 resolved by live probe; six vendor-contract corrections

## LES-051 — When a timestamp API's precision is coarser than the extraction API's, a threshold is needed before "discontinuity" means "outage"

**Scope:** `acquire/catalog.py` (gap detection), any code comparing timestamps sourced from two APIs with

## LES-059 — Submitting all work upfront to a `ThreadPoolExecutor` and relying on `Future.cancel()` to "stop admitting" is racy against the pool's own work-stealing

**Class:** tool-gotcha
**Scope:** `acquire/harvest/pipeline.py`
**Consumers:** code-writer, code-reviewer, tester
**Rule:** Do not submit an entire batch of work to a `ThreadPoolExecutor` upfront and then try to "stop
admitting more" on shutdown/SIGINT by calling `Future.cancel()` on the not-yet-started ones —

## LES-063 — A Scope: token's bare-word match depends on what physically exists on disk at match time — gitignored directories included

**Class:** tool-gotcha
**Scope:** `scripts/inject_lessons.py`, "any `Scope:` token in `docs/LESSONS.md`", "gitignored directory affecting a bare Scope token"
**Consumers:** doc-writer, code-writer, code-reviewer, tester
**Rule:** `inject_lessons.py`'s bare-token match (`scope_matches`) requires the token to be a directory name discovered by walking the real filesystem from the repo root to `max_depth=3` — and that walk uses `Path.iterdir()`, which sees every directory that physically exists, **including one `.gitignore` excludes from version control**. This round's bare `zeek` Scope token (pre-dating this merge) was found auto-injecting onto `acquire/harvest/zeek.py` — a file whose own path segments trivially contain "zeek" (from its basename), matched against a "zeek" directory the walker found not at `ingest/zeek/` (four levels deep, past `max_depth`, and so in fact NOT walked) but at `metadata/zeek/` — a real, present, gitignored capture-data directory sitting two levels down from the repo root. ## LES-064 — `except ImportError` around a lazy optional-extra import must discriminate on `exc.name`, or every bug in a present package is reported as "not installed"

**Class:** bug-class
**Scope:** `src/aximprint/cli.py`, `acquire/__init__.py`, "any lazy optional-dependency import guarded by `except ImportError`"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** A guard of the shape `try: import requests \n except ImportError: raise MissingExtraError("pip install -e '.[acquire]'")` is correct only for the one `ImportError` it means to catch — `requests` itself missing — and wrong for every other `ImportError` that can legitimately surface from the same `import` statement or from anything it transitively imports: a genuine bug in an installed package (a bad `from foo import name_that_moved`), a broken transitive dependency, or a real syntax/version mismatch inside `requests` itself all raise `ImportError` too, and a bare `except ImportError` reports **all of them** as "please install the extra" — which is actively misleading when the extra *is* installed and the real problem is something else. Discriminate on `exc.name` (the dotted module name Python attaches to the exception, e.g. `"requests"`): only an `ImportError` whose `name` equals the dependency you were trying to import means "not installed"; anything else must re-raise (or wrap with the real cause preserved), never be swallowed into the same "install the extra" message. This is `LES-038`'s discipline ("never assert a body the docs don't document") applied to Python's own import machinery: don't let a broad `except` clause assert a diagnosis it hasn't actually confirmed.
**Origin:** CHANGELOG 2026-08-10 (xtract→acquire merge, `docs/WORK_ORDER_merge_xtract_acquire.md`, D4 validation: "a missing extra must fail loud with a message naming it"); `LES-038`.

## LES-065 — `sys.modules[name] = None` tests an absent dependency only if `name` is the dependency, not your own module — and only if nothing has transitively imported it yet in that process

**Class:** tool-gotcha
**Scope:** `tests/acquire/`, "any test simulating an absent optional dependency", "sys.modules"
**Consumers:** tester, code-writer, code-reviewer
**Rule:** Setting `sys.modules[name] = None` before an `import name` statement is a real, documented CPython idiom for forcing that import to raise `ImportError` without actually uninstalling anything — but it has two preconditions a test author can get wrong in ways that don't fail loudly. First: `name` must be the actual dependency being simulated as absent (`"requests"`), **not** your own wrapping module (`"aximprint.acquire.client"`) — patching your own module's entry only breaks importing *that* module, which is a different and much less interesting failure than "the optional dependency is missing," and a test that does this can pass while testing nothing like the scenario it claims to. Second: the patch only affects imports that happen **after** it is set — if some other module already imported and cached the real dependency earlier in the same pytest process (e.g. a fixture, an earlier test, or a `conftest.py` that imported `acquire` eagerly), code holding that earlier reference keeps working fine, and only a *fresh*, lazy, function-scoped `import` after the patch will observe the simulated absence. A test written and passing in isolation can therefore stop meaningfully testing anything the moment test collection order changes and something else imports the dependency first — always reset `sys.modules` in a fixture teardown, and be suspicious of any such test that doesn't run in a fresh subprocess or doesn't control import order explicitly (the same "look complete, isn't" shape as `LES-020`'s registry-by-import-side-effect trap).
**Origin:** CHANGELOG 2026-08-10 (xtract→acquire merge, `docs/WORK_ORDER_merge_xtract_acquire.md`, D4 packaging tests); `LES-020`.

## LES-074 — A permanent failure modeled as a subclass of a transient one silently inherits the retry policy; catch order is the fix, and it is load-bearing

**Class:** error-taxonomy
**Scope:** `src/aximprint/acquire/client.py`, `src/aximprint/acquire/errors.py`, "any `except` clause catching a library exception base class", "retry loop", "requests.exceptions", `tests/acquire/test_client.py`
**Consumers:** code-writer, code-reviewer, tester
**Rule:** `requests` models a TLS verification failure as `SSLError`, a **subclass of its own `ConnectionError`**. A retry loop written as `except (requests.exceptions.ConnectionError, requests.exceptions.Timeout)` therefore catches certificate rejections too, and retries them the full budget — here four handshakes and 3.5 s of backoff to re-learn that a certificate the appliance will present again is still not verifiable. The bug is invisible at the call site: the code reads as "retry transient transport faults," and the taxonomy quietly widens "transient" to include something permanent. **`client.py` already knew the principle and stated it in the very docstring above the bug** — "`418` (and every other 4xx) is never retried — it's a stable answer, not a transient failure (`LES-035`)" — and the principle was violated one layer lower anyway, because at HTTP level the stable answers arrive as *status codes* you must opt into retrying, while at transport level they arrive as *exceptions* you must opt out of. Same distinction, opposite defaults, and the default is the one that bites. **Generalizes to every `except` on a library base class: before catching one, check what inherits from it** — `requests.exceptions.SSLError` under `ConnectionError`, `socket.timeout` under `OSError`, `json.JSONDecodeError` under `ValueError`. Where a subclass needs different handling, its clause goes **first**, and that ordering is load-bearing — a later "tidy the except clauses" edit that reorders them alphabetically or by frequency silently restores the bug, so say so in a comment and pin it with a test that asserts the *attempt count* under a non-zero retry budget (`max_retries=2`, not `0` — a budget that exists and must go unspent is the only version of that test that can fail). Corollary for the message: a `type(exc).__name__`-only error string, correct as it may be for privacy (`LES-039`), reduces an entire failure family to one word — "SSLError" spans a no-SAN certificate, an untrusted CA, an expired certificate and a protocol mismatch, which do not share a remedy. Naming the *remedies* costs no privacy, because a flag name is not a hostname.
**Origin:** CHANGELOG 2026-08-11 (`acquire`: three operator-reported CLI defects); user report of `POST /axapi/login failed after 4 attempt(s): SSLError`; `LES-035` (418 is a stable answer), `LES-039` (transport exception text must never reach the manifest).

## LES-080 — A measured concurrent outcome is not a property until you prove it's deterministic

**Class:** determinism-trap
**Scope:** "any test asserting an exact count or value produced by concurrent or racing code", `tests/acquire/test_cli_harvest.py`, `tests/acquire/test_pipeline.py`, "SIGINT/interrupt-drain test"
**Consumers:** tester, code-writer, code-reviewer

## LES-088 — Presence says a stem appears; only content says it carries something new. Rule a data source in on what it uniquely contributes, and name the fields it must refuse in the same breath

**Class:** coverage-ruling
**Scope:** `src/aximprint/ingest/zeek/plugin.py`, `_PARSERS`, `_COLUMNS`, `src/aximprint/windowing/windows.py`, `SERVICE_PROJECTIONS`, "admitting a new log type, log stem, telemetry stream or upstream data source into the event model"
**Consumers:** code-writer, code-reviewer, doc-writer
**Rule:** Two failures compound when a new data source is admitted, and both were live in `Q24`. **First: frequency is not value.** `Q24` was drafted with a presence table (12/12, 8/12, 4/12 windows) and recommended the eight stems at 12/12 — a ranking by how often a stem *appears*, which says nothing about whether its content is new, attributable to an entity, or safe to keep. ## LES-089 — "Is this useful?" is unanswerable until you name WHICH consumer; a test scoped to one silently rejects everything the others need

**Class:** coverage-ruling
**Scope:** `src/aximprint/ingest/zeek/plugin.py`, `_PARSERS`, `_COLUMNS`, `src/aximprint/windowing/entities.py`, `SERVICE_PROJECTIONS`, "declining a data source as redundant", "deciding what a parser extracts"
**Consumers:** code-writer, code-reviewer, doc-writer
**Rule:** **Generalized 2026-08-13 after this lesson's own narrow form failed a third time.** The pipeline has **three declared outputs** — `twin_config` (structure), `tfc` (behavior: "fitted intensities/schedules/seeds"), `tap` (vantage) — plus provenance obligations that cut across all of them (DESIGN_BRIEF §9). **A usefulness test that names none of them will silently adopt whichever one the author had in mind, and reject every source the other two need.** That happened three times in one round of `Q24`, each time producing a *confident* decline:

1. **Scoped to observed entities** → rejected LDAP DNs, SMTP `Received:` chains, x509 SANs — sources whose whole value is entities `conn` never names.
2. **Scoped by disclosure** → rejected `smtp`/`sip` and stripped fields from admitted parsers, until privacy was retired as a principle (CONVENTIONS §3, 2026-08-12).
3. **Scoped to `twin_config`** → rejected `ocsp`, whose `nextUpdate − thisUpdate` is a cache lifetime, i.e. exactly the *schedule* `tfc` is made of; and left `_COLUMNS["ntp"]` dropping `poll`, a poll interval, for the same reason. Neither is a fact about a host, and both are load-bearing for what the twin must **emit**.

**The working test, stated so it cannot quietly narrow again:** a source earns a parser if it supplies (a) a fact no other source carries, (b) an **entity** no other source names, or (c) a **behavioral parameter** — rate, interval, cache lifetime, schedule, mix — that no other source supplies. Answer all three explicitly; "it's redundant" without saying *for which output* is not an answer. And note the asymmetry that makes this failure mode stubborn: a wrong *admit* costs some parse time and shows up as an unused table, while a wrong *decline* is invisible — the evidence simply never arrives, and nothing downstream reports its absence.

Two corollaries from the original form, both still live:

- **Redundancy buys confidence only between *independent* witnesses.** `ssl.subject` and `x509.subject` come from the same handshake, same analyzer, same packets — recording both is one observation written twice. An `ntlm` hostname, a DNS PTR and a DHCP hostname are independent paths to one binding, and their agreement is real corroboration.
- **Before declining anything as redundant, check whether the store can even hold what the new source produces.** Two channels are missing today and each blocks a different class of evidence: `windowing/entities.py` drops any binding without an IP (`if not (ev.ip and other): return None`), so a host known only by name has no subject and `referenced` has no emitter (`Q1`); and nothing at all accepts a **subject-less** fact, so a population-level `tfc` parameter has nowhere to land (`Q29`). Those absences, not privacy and not parse cost, are what actually gate this evidence.

**The original, narrower rule (2026-08-12), kept because it is the clearest single instance:** rejecting a data source because "that fact already arrives from X" is valid **only over the entity population X names.** In `Q24` the test was "does this stem carry a durable fact no already-parsed stem carries," and applied against a corpus where `conn.log` names every host the sensor observed, it is nearly a tautology: any *service* fact about an *observed* host looks partly redundant, so the test systematically rejected exactly the stems whose value lies with entities `conn` never names at all — **LDAP distinguished names** (computer accounts, users, OUs), **SMTP `Received:` chains and `x_originating_ip`** (addresses of relays and originating clients on segments the tap does not cover), **x509 SANs** (many hostnames per certificate, versus `ssl.subject`'s one). "Serves LDAP already arrives via `known_service`" is true for hosts already in the store and vacuous for the hosts that make the stem worth parsing. **The corrected test has two clauses: a fact no other source carries, OR an entity no other source names.** Two corollaries worth carrying: (a) **redundancy buys confidence only between *independent* witnesses** — `ssl.subject` and `x509.subject` come from the same handshake, same analyzer, same packets, so recording both is one observation written twice, whereas an `ntlm` hostname, a DNS PTR and a DHCP hostname are independent paths to one binding and their agreement is real corroboration; (b) before declining anything as redundant, check whether the store can even *hold* the subject the new source names — here `windowing/entities.py` drops any binding without an IP (`if not (ev.ip and other): return None`) and `resolve()` is address-in/address-out, so a host known only by name has no subject, and the `referenced` evidence class that exists for exactly this case (DESIGN_BRIEF §7, `learners/extractors.py`) has **no code path emitting it**. That absence, not privacy and not parse cost, is what actually gates this class of evidence (`Q1`).
**Origin:** CHANGELOG 2026-08-12 and 2026-08-13 (`Q24` amended three times across two days, every amendment prompted by the user spotting a scope the test had silently excluded); `docs/WORK_ORDER_zeek_stem_coverage.md` D2/D3 amendments; DESIGN_BRIEF §9 (the three outputs); `Q1` and `Q29` (the two missing store channels), `Q26`, `Q27`; `LES-088` is the adjacent half — presence does not imply content, this one is content does not imply coverage.

## LES-092 — A column reached only through `_attrs()` must stay text end to end in the archive; a typed column changes the VALUE, not just its representation

**Class:** determinism-trap
**Scope:** `docs/SPEC_zeek_metadata_archive.md`, `src/aximprint/ingest/zeek/plugin.py`, `_attrs()`, `_s()`, "choosing a DuckDB/Parquet column type for a field a parser stores as a string", "transport equivalence"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** `_attrs()` (`ingest/zeek/plugin.py`) stores every attribute it collects as a string, unconditionally, and never re-parses it numerically — so an archive converter's column type for such a field is not a free choice, even though nothing downstream appears to consume the type. A DOUBLE/BIGINT column is a **conforming** archive (every read-time check passes) that silently breaks transport equivalence anyway, because DuckDB hands back a native Python value whose `str()` does not reproduce Zeek's on-the-wire text: an `ntp.log` `poll` interval written as `"64.000000"` on the TSV transport becomes `str(64.0) == "64.0"` once typed DOUBLE — same value, different bytes, and the CLI round-trip / transport-equivalence gate is exactly what would catch the drift, quietly, on whichever field widens next. `docs/SPEC_zeek_metadata_archive.md`'s Columns section now states this as a normative rule: a converter may choose any type for an `_attrs()`-only column **as long as it is VARCHAR**. The `vector`/`set` case is a *different* failure and must not be handled the same way: a Parquet `LIST` column doesn't mis-format, it **raises**. `_s()` used to test `v in _UNSET` directly — `TypeError: unhashable type: 'list'` on a native list, the shape both JSON-lines and DuckDB's `LIST` hand back for a `vector[string]`/`set[string]` field (e.g. `ldap_search.attributes`) — a crash on a perfectly conforming log, not a quiet value drift. Fixed by joining a `list`/`tuple` on `,` before the unset check ever sees it, matching Zeek's own TSV convention for the same field (`answers`/`TTLs` already relied on this). Two different failure shapes from one root cause — a column typed richer than the string `_attrs()` promises — so a fixture/test suite needs both a numeric-looking `_attrs()` field and a vector-typed one, not just one or the other.
**Origin:** CHANGELOG 2026-08-13 (build steps 2/2b land, code-review round); `docs/SPEC_zeek_metadata_archive.md` "Columns"; `src/aximprint/ingest/zeek/plugin.py::_s()`; `tests/test_zeek_ingest.py::test_vector_field_from_json_lines_does_not_crash_s`; `tests/test_zeek_parquet_source.py::test_widened_service_columns_are_projected_on_the_archive_transport`.

## LES-094 — A reader that infers columns from a path silently beats the file's own data; turn the inference off at the call site, don't avoid the colliding names forever

**Class:** silent-default-trap
**Scope:** `src/aximprint/ingest/zeek/sources.py`, `ParquetArchiveSource`, `docs/SPEC_zeek_metadata_archive.md`, "any `duckdb.read_parquet`/columnar read over a Hive-style partitioned layout", "a data column whose name collides with a partition-key name"
**Consumers:** code-writer, code-reviewer, tester
**Rule:** DuckDB's `read_parquet` infers partition columns from the directory path by default (Hive-partitioning `true` is the implicit behavior), and when a partition key's name collides with a real column inside the file, the partition-inferred value silently **shadows** the file's own — verified empirically: `read_parquet('<one file>', hive_partitioning=true)` over this archive's `log=<stem>/date=<D>` layout returns the *partition's* calendar date for a column literally named `date`, discarding the row's real content, with no error raised. `smtp.log`/`sip.log` both carry a real `date` field (the message's own `Date:` header) that collides. ## LES-106 — A generator that computes a fact before its first `yield` publishes it after exactly one `next()` — and loses that guarantee to any wrapper, any caller that never iterates, and any later `yield` moved above it

**Class:** ordering-invariant
**Scope:** `src/aximprint/ingest/zeek/plugin.py`, `ZeekPlugin.events`, "a generator function that computes a run-level fact synchronously before its own first `yield`", ingest, zeek, windowing
**Consumers:** code-writer, code-reviewer, tester

## LES-121 — Ranking metrics can be above chance while the confident end is pure noise; a fail-closed design is judged only at that end

**Class:** pattern
**Scope:** "model evaluation", "classifier threshold", "AUC", "any inference feeding a fail-closed guard", `docs/WORK_ORDER_ml_layer.md`
**Consumers:** code-writer, code-reviewer
**Rule:** An unsupervised host-identity linker reached **AUC 0.741** against 421 held-out true pairs — comfortably above chance, and the number one would naturally report. ## LES-145 — Do not reduce across evidence classes at the layer that cannot import the ranking; return every reading and resolve on the conclusions side

**Class:** pattern
**Scope:** `store`, `src/aximprint/store/belief_store.py`, `ir`, `src/aximprint/ir/materialize.py`, "snapshot", "evidence_class", "evidence_rank", "max(confidence)", "the strongest evidence", "in_segment", "has_role"
**Consumers:** code-writer, code-reviewer
**Rule:** `BeliefStore.snapshot()` reduced two evidence classes for one fact to a single winner using `max(confidence)`. It was right only by arithmetic accident — `SEGMENT_EVIDENCE` supplies `(observed, 0.95)` and `(imputed, 0.6)`, which rank the same way twice — and it was about to be wrong the moment a class could break the coupling (`asserted` at 1.0, or an `imported` row outranking `observed` at a per-source confidence below 0.95). The obvious repair is to sort on the rank; the better one is **to stop reducing there at all**. Three reasons, in order of weight: **(1)** the model's own house rule is *"the store keeps both readings, and an override is visible, never an erasure"* — a reduction erases the loser before anything can name it in the artifact whose job is naming it; **(2)** the ranking lives in a layer the store may not import, so ranking in place would mean a **second rank table** duplicating the vocabulary it ranks (`LES-101`); **(3)** the resolver is pure and the conclusions layer already takes a frozen snapshot, which is where a total order `(rank, -confidence, value)` can be written once and tested against hand-built pairs. **The general shape: a reduction that discards evidence belongs where the ranking is DECLARED, not where the rows happen to be read.** When you find one at the wrong layer, check whether the correct layer already exists before adding a table to the wrong one.

## LES-146 — A canonical re-emitter must round-trip through its own parser; a value normalized at parse time is a value the writer has to un-normalize

**Rule:** The assertions parser converts an authored `listen: [{port: 88, proto: tcp}]` into the `"88/tcp"` strings the IR joins against — correct, and done once so the two forms are related in one place.
